# Design: Layer B 자체 호스팅 registry — 지금 production화할 것인가

Generated by /office-hours on 2026-06-09
Branch: main
Repo: design_system (WONIK IPS Design System)
Status: APPROVED
Mode: Startup (intrapreneurship — 사내 프로젝트)

## Problem Statement

표면 질문: "리허설을 통과시킨 Layer B 자체 호스팅 npm registry(테스트 PC + 작업 스케줄러 always-on)를 지금 정식 production으로 굳힐 것인가?"

진짜 질문(office-hours에서 재구성됨): "회사 웹 전체의 **통일된 디자인(DS 채택)**을 달성하는 데, registry가 **다음 최고 레버리지**인가?" — 아니다. registry는 배급 파이프이고, 현재 병목은 배급이 아니라 **채택**이다.

## Demand Evidence

**오늘 수요 = 0.** 사용자 본인이 먼저 인정 — *"아직은 곤란한 사람이 없어 다들 바이브 코딩으로 만들면 되니까."*

- 첫 dogfood인 ppt는 CLAUDE.md 기준 **workspace-link로 import** → registry 불요.
- 사내 다른 소비처는 아직 미등장. AI팀은 바이브코딩 중이며 `@wonik/web` 채택에 합의한 적 없음.
- *"DS를 무조건 써야 된다"* 는 사용자의 **판단(확신)**이지, 강제된 조직 수요가 아니다. (내부 도구판 "interest is not demand".)

즉 registry가 오늘 사라져도 곤란해지는 사람이 없다. 배급 인프라를 **소비자보다 먼저** 깔고 있는 상태.

## Status Quo

- 사내 웹앱에는 디자인 표준이 없다. → **AI팀이 바이브코딩으로 뽑는 것이 "사실상 표준"으로 굳어가는 중.** 사용자(UX 디자이너)가 막아야 하는 핵심 문제는 이 *무표준의 디폴트화*다.
- 패키지 배급 현황: ppt 한정 workspace-link. 그 외 통로 없음.
- 사용자 본업 = HMI(상시 제작). → DS + registry 유지에 쓸 대역폭이 애초에 제한적. 솔로 유지비가 최대 제약.

## Target User & Narrowest Wedge

- **진짜 소비처 = AI팀**(사내 웹앱 개발 주체).
- **Narrowest wedge = "AI팀이 만드는 결과물이 `@wonik/web`로 만들어지게 하는 것."**
- 이 wedge는 **배급(registry) 문제가 아니라 채택 문제**다. 채택을 만드는 forcing function 3종: ① 리더십 명령(디자인 리뷰 게이트) ② 최소저항경로(AI 컨텍스트 침투) ③ 직접 검수. 셋 다 registry가 아니다.

## Constraints

- 솔로 메인테이너 + HMI 본업 → **유지비가 최대 제약.**
- 사용자 자신의 규칙: **ADR-001**(진짜 product 등장 전 speculative 추상화/인프라 금지), MVP scope discipline.
- 회사-종속 액션(사내 IT 협의, 사내 registry 확인 등)은 **사내 환경 진입 시까지 push 대기**.

## Premises (전부 동의 확인됨)

1. 목표(회사 웹 전체의 통일된 디자인 = DS 채택)는 정당하다. — ✅
2. 오늘 수요는 0이다 (`@wonik/web`를 요청·못 받아 막힌 소비처 없음). — ✅
3. "무조건 써야 된다"는 **아직 사용자의 판단이지 조직적 forcing function이 아니다** (리더십 명령/리뷰 게이트 현재 없음). — ✅ **사용자 인지: "리더십 명령이 가도록 만들어야지" (= 명령은 제조해야 할 대상).**
4. registry는 채택을 만들지 않는다 (배급 파이프일 뿐, 강제 장치 아님). — ✅
5. 따라서 다음 최고 레버리지는 registry 하드닝이 아니라 **채택 forcing-function**이다. — ✅

## Approaches Considered

### Approach A: 동결 + 명령 피벗  (minimal viable)
- Summary: registry를 "self-host 가능 검증됨 / 소비처+명령 생기면 해동"으로 ADR에 박아 동결. 에너지를 리더십 명령 제조로 이동.
- Effort: S · Risk: 낮음
- Reuses: 리허설 작업(검증필 옵션으로 보존), `/wonik.center-lead`·`/wonik.group-lead`.

### Approach B: 명령 피벗 + 배급은 사내 IT에 위탁  (ideal architecture)
- Summary: WONIK에 IT가 굴리는 사설 registry(Nexus/Artifactory/GitHub Packages)가 있으면 그 사설 scope에 publish = 솔로 유지비 영구 0. 테스트 PC registry는 production에 안 감.
- Effort: M · Risk: 낮음~중 (IT 의존)
- 단, IT 협의는 **사내 환경 진입 시**. 그리고 명령이 실제로 떨어진 *다음에* 의미가 생김.

### Approach C: AI팀 컨텍스트 침투  (creative / lateral)
- Summary: AI팀이 바이브코딩하므로 배급을 npm이 아니라 **그들의 AI 컨텍스트**(공유 CLAUDE.md·컴포넌트 레퍼런스·스타터 템플릿·MCP)에 주입. DS 쓰는 게 바이브코딩보다 쉬운 길이 되면 채택이 자가발생.
- Effort: M · Risk: 중 (AI팀 툴체인·의지 의존)
- Reuses: 이미 만든 tokens·web, 사용자의 metacog/wiki 습관.

### Approach D: 지금 production 하드닝  (status quo / 기각)
- Summary: 로드맵 방향대로 테스트 PC를 정식 registry로 굳힘.
- 기각 사유: 소비처 0인데 본업 있는 솔로가 **책상 PC를 production 단일장애점**으로 떠안음 + ADR-001·MVP 규율 위반 + 순서가 거꾸로. (작동은 하지만 지금 할 일이 아님.)

## Recommended Approach — **A+C 병행** (사용자 선택)

**A (top-down, 본선):**
1. registry 동결을 ADR로 기록 — 검증된 것/동결 이유/**해동 트리거**를 명시 (해동 조건은 아래 Open Questions 참조).
2. `/wonik.center-lead`로 임원용 1페이지 피치 1개 작성. 핵심 메시지: *"표준이 없으면 AI팀의 제각각 결과물이 회사 표준이 된다"* 는 비용. **registry 얘기는 한 줄도 넣지 않는다** (리더십 관심사 아님).
3. `/wonik.group-lead`로 그룹장 1-on-1에 올릴 사전 통보형 어젠다 준비.

**C (bottom-up, 병행 다리):**
1. **먼저 AI팀 수용성 타진 (대화 1회).** "DS를 컨텍스트에 넣어줄 테니 써볼래?"에 열려 있는지 확인. ⚠️ 이 단계를 건너뛰고 침투 아티팩트(CLAUDE.md·템플릿)부터 만들면 — *받을 의지가 없는 소비자에게 배급물부터 만드는* registry의 실수를 그대로 반복한다.
2. AI팀이 쓰는 코딩/AI 툴 파악(Claude Code / Cursor / 기타) — C의 침투 통로가 여기 달림.
3. `@wonik/tokens` + `@wonik/web`를 AI가 읽을 형태로 패키징: 공유 CLAUDE.md 규칙 + 컴포넌트 레퍼런스 + (가능하면) 스타터 템플릿. "이걸 컨텍스트에 넣으면 바이브코딩 결과가 자동으로 표준"이 되게.
4. AI팀 신규 웹앱 1개에 시범 적용 → 첫 외부 채택 = 명령 피치의 결정적 근거가 됨.

두 다리가 서로 강화한다: C가 "이미 반쯤 쓰이고 있다"를 만들면, A의 리더십 명령은 형식적 절차가 된다.

## 후속 갱신 (2026-06-09) — 타임라인 확정

사용자 방침: **지금 표준 강제 요청 안 함.** 프로젝트를 **내년까지** 끌고 가 *충분히 다듬어 완성형으로* launch. → 센터장 피치는 **내년용 보관 자산**(지금 발사 X).

단, "혼자 다듬기"는 office-hours 경계 패턴("완벽해질 때까지 출시 미루기")이므로 — **올해의 일 = 실사용 기반 polish.** 실빌더 포함 테스터 섭외, *retention*·*real-ship* 기준으로 다듬음(C 다리 = 자발적 채택이 통로). **"완성"의 정의 = 소비처의 실제 화면을 받아냄**(= 끝선; 소비처 없으면 스코프 무한 발산 → ADR-001·ADR-034 위반). 즉 테스터가 "완성"에 끝선을 준다.

## Open Questions

- 리더십 명령을 **누구에게**(센터장? 그룹장?) **어떤 형태**(디자인 리뷰 게이트? 정책 문서? 표준 선언?)로 받을 것인가?
- AI팀의 실제 코딩/AI 툴체인은? (C의 침투 통로 결정)
- WONIK에 IT-managed 사설 registry가 이미 존재하는가? (B의 전제 — 사내 환경서 확인)
- **해동 트리거 정의**: 어떤 사건이 registry production화를 정당화하나? → 후보: "별도 repo에 있고 workspace-link로 못 받는 실재 소비처 + 채택 명령"이 동시에 성립할 때.

## Success Criteria

- **올해(this year)**: 실빌더 포함 테스터 섭외 완료. **`@wonik/web`로 ship된 실제 사내 화면 ≥1 + 테스트 후 계속 쓰는 사람 ≥1**(retention = 진짜 demand 신호). registry 동결 ADR 1건.
- **내년(launch)**: 다듬어진 완성형 + 실전 레퍼런스를 손에 쥐고 센터장 피치 발사 → 리더십 권고/리뷰 게이트.
- **가짜 성공 경계**: "N명이 좋대"(만족도)는 신호 아님 — **retention / real-ship만** 카운트.

## Distribution Plan

- 현재: ppt workspace-link 유지 (registry 불요).
- 진짜 소비처(AI팀, 별도 repo) 착륙 시 — 가장 싼 통로 순서로: ① IT-managed 사내 registry에 사설 scope publish > ② git dependency > ③ 자체 호스팅 always-on registry는 **최후**.
- 자체 호스팅 registry = 동결된 "검증필 옵션"으로 보존 (리허설 결과는 폐기 아님, 대기).

## Dependencies

- center-lead/group-lead 산출물(피치·어젠다).
- 사내 환경 진입 (IT 확인, 리더십 접근, AI팀 툴체인 파악).
- AI팀의 협력 의지 (C의 시범 적용).

## The Assignment

**올해(내년 launch 전까지):** 실빌더(자기 진짜 사내 화면을 `@wonik/web`로 만드는 사람)를 **최소 1명 포함**해 테스터 여러 명 섭외. 가이드 데모 말고 **진짜 task 주고 안 도와주고 관찰**(막히는·놀라는 지점이 신호). 성공 = "만족도"가 아니라 **retention(테스트 끝나고도 계속 씀) ≥1 + 실제 화면 1개 ship**. 그들의 고통 리스트가 polish 백로그가 된다.

센터장 피치는 이미 초안 존재(`center-lead-pitch-2026-06-09.md`) → **내년 보관 자산. 레퍼런스(ship된 실화면 1개)가 붙으면 발사.** registry는 동결 유지.

## 약한 가정 (self-review — 외부 리뷰어 불발, 작성자 적대적 점검으로 대체)

1. **가장 약한 가정 — C의 진입점.** A+C는 AI팀이 *당신이 그들의 워크플로우에 DS를 주입하는 걸 받아들인다*고 가정한다. 받을 의지가 없으면 C는 진입점 자체가 없다 → 그래서 C 1단계를 "아티팩트 제작"이 아니라 "수용성 타진"으로 바꿨다(위 참조).
2. **리더십 명령은 가장 느리고·가장 통제 밖이다.** "명령이 가도록 만든다"는 몇 달~분기가 걸리거나 끝내 안 올 수도 있다. C(bottom-up)가 그 헤지다 — 명령이 안 와도 "이미 반쯤 쓰이는" 상태는 만들 수 있다. 하지만 *명령이 영영 안 오면 bottom-up만으로 회사 전체 표준이 되는가*는 미해결(부분적으로만 그렇다).
3. **A·C 실행은 사내 환경 종속이다** (리더십·AI팀 접근). 집에서 가능한 건 *피치 초안 작성*과 *C 아티팩트 프로토타이핑*까지 — 실제 대화/착륙은 사내에서. Assignment(피치 1페이지 뽑기)는 집에서 가능하도록 잡았다.

## What I noticed about how you think

- *"아직은 곤란한 사람이 없어 다들 바이브 코딩으로 만들면 되니까"* — 대부분이 "다들 쓸 거다"로 얼버무리는 수요 부재를, 당신은 먼저 인정했다. 진단의 절반은 거기서 끝났다.
- *"그래서 DS를 무조건 써야된다라는게 내 판단이야"* — "판단"이라는 단어를 당신이 직접 썼다. 확신과 강제를 구분할 재료를 내가 끌어낸 게 아니라 당신이 줬다.
- *"리더십 명령이 가도록 만들어야지"* — 전제 3번에 압박을 받자 방어하지 않고, 진짜 레버를 스스로 집었다. registry에서 forcing-function으로 무게중심을 옮긴 그 한 문장이 이 세션의 전환점이다.
