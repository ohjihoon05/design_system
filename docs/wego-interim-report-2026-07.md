## 1. 요약 (30초)

본 과제의 목표는 **사내 웹 서비스의 UI/UX 표준화**이며, 그 실행 수단이 **디자인 시스템**(표준화된 화면 부품 체계) 구축입니다. 상반기 실적 3줄:

1. **표준 부품 시스템 v1.0 구축 완료** — 화면 부품(컴포넌트) 25종 + 표준값(토큰) 체계, 자동 테스트·접근성 검증 포함.
2. **실사용 환경 검증 완료** — 표준 부품을 실제 소비하는 사내 업무 도구가 사용자 2명의 실업무 환경에서 정상 동작함을 확인.
3. **웹 외 플랫폼 확장 기반 완성** — 표준값 원본 하나에서 웹(React)·Vue·Flutter(앱) 3개 기술용 표준 파일이 자동 생성되는 파이프라인 구축·검증. 사내 Vue·Flutter 앱 팀의 통합 요청에 대응 가능한 상태.

하반기는 **확산**(사용 팀 늘리기)과 **Vue·Flutter 컴포넌트 착수**가 중심입니다.

## 2. 과제 배경 — "UIUX 표준화"가 왜 디자인 시스템인가

**문제**: 사내 웹 화면이 만드는 사람(팀·외주·자동 생성 도구)마다 제각각입니다. 색·간격·버튼 모양이 화면마다 다르고, 회사 CI 컬러(WONIK BLUE #273E82)조차 화면마다 다른 파란색으로 구현되는 상태입니다. 이대로 두면 제각각 화면이 사실상의 회사 표준으로 굳어지고, 되돌리는 비용은 매년 커집니다.

**접근**: 표준화를 문서(가이드 PDF)로 하면 지켜지지 않습니다. 대신 표준을 **재사용 가능한 부품**으로 만들어, 부품을 가져다 쓰기만 하면 표준이 자동으로 지켜지는 구조를 만들었습니다. 이것이 디자인 시스템이며, 두 축으로 구성됩니다:

| 축 | 내용 | 산출물 |
|----|------|--------|
| **표준 정의** | 색·글자·간격·부품 생김새의 기준을 디자인 도구(Figma)에 정의 | Figma `Standardization 2.0` 파일 — 웹 Light/Dark 팔레트·버튼·테이블 표준 + HMI(장비 화면) 마스터 컴포넌트 27종 |
| **표준 집행** | 그 기준을 개발자가 그대로 가져다 쓰는 코드 부품으로 제공 | 코드 패키지 `@wonik/tokens`(표준값)·`@wonik/web`(화면 부품 25종) |

두 축은 전수 대조로 정합을 유지합니다(값이 어긋나면 코드 쪽 감사 기록으로 교정 — ADR-021~025).

## 5. 성과 상세

### 5-1. 표준 부품 시스템 v1.0 (웹)

버튼·입력창·표·모달 등 사내 웹 화면에 필요한 부품 25종을 표준값 기반으로 구현했습니다. 특징:

- **CI 내장**: WONIK BLUE(#273E82)가 부품에 박혀 있어, 쓰는 사람이 색을 틀릴 수 없음.
- **Light/Dark 모두 지원**: 반도체 장비 모니터링 등 어두운 화면 수요 반영.
- **접근성(WCAG) 검증**: 색 대비·키보드 조작·최소 클릭 영역(24×24px) 기준을 자동 검사 도구(lint + Storybook)로 상시 가드.
- **도메인 특화**: alarm/run/processed 등 반도체 장비 상태색 표준 — 일반 상용/오픈소스 디자인 시스템에 없는 자산.

### 5-2. 실사용 환경 검증 — "만든 것"이 아니라 "실환경에서 돌아가는 것" (ADR-046)

디자인 시스템의 성공 지표는 산출물 개수가 아니라 **채택**입니다(ADR-044). 그 첫 단계인 실사용 환경 검증을 6/24 종결했습니다:

- 본 시스템의 부품 8종 이상을 실제 소비하는 사내 발표자료 제작 도구(ppt)가, **사내 사용자 2명**(SQA 내부 1명 + 타부서 1명)의 실업무 환경에서 정상 동작함을 확인.
- 부품 소비 여부는 코드 수준에서 검증 — 전시용 데모가 아닌 실제 업무 도구 기준.
- 의미: 본 시스템은 실환경 동작이 확인된 자산. 단, 지속 사용·확산 증명은 하반기 과제(§7).

### 5-3. 멀티플랫폼 확장 기반 — 표준값 단일 원본 (ADR-047)

사내에는 웹(React) 외에 **Vue 웹앱과 Flutter 앱**이 실재하며, 해당 앱 팀들이 통합 디자인 시스템을 직접 요청했습니다(본 과제 역사상 처음으로 수요처가 먼저 온 사례). 이에 대응:

- 표준값 원본 하나에서 **웹 CSS·Vue CSS·Flutter Dart 파일이 자동 생성**되는 파이프라인 구축. 국제 표준 포맷(DTCG)과 1:1 호환되는 토큰 구조를 4개월간 유지해 온 결과, 변환기 연결만으로 달성.
- **책상 검증에 그치지 않고 실소비 테스트 수행**(7/9): 실제 Vue 앱·Flutter 앱을 새로 만들어 산출물을 투입 → Vue는 브라우저 렌더에서 CI 컬러 일치까지 확인, Flutter는 결함 2건(명명 규칙 위반·타입 지뢰)을 **발견하고 수정 후 재검증 통과**. 유닛 테스트만으로는 못 잡는 종류의 결함으로, 검증 방식 자체의 가치가 입증됨.

### 5-4. HMI(장비 화면) 표준 — Figma 라이브러리 v1

장비 HMI는 코드 배포가 아닌 Figma 라이브러리가 표준 그릇이라는 판정(비용 대비) 하에, `Standardization 2.0` 파일에 **마스터 컴포넌트 27종 정리 + StateChip 신규 제작**을 완료했습니다(6/12). HMI 색 사용 원칙(무채색 베이스 + 신호색 예약)도 표준으로 확정했습니다(ADR-037).

## 6. 수행 방식 — 품질과 비용을 어떻게 통제했나

1인 수행 과제이므로 "많이 만들기"가 아니라 **증거 기반 + 비용 절제**로 운영했습니다.

- **모든 결정을 기록**: 표준·구조 결정 45건을 근거·트레이드오프와 함께 ADR로 문서화 — 담당자 부재 시에도 결정 맥락이 남는 구조.
- **테스트 우선(TDD) + 실소비 검증**: 기능 구현 전 테스트 작성이 원칙. 추가로 실제 소비 환경을 재현하는 dogfood trial 15회로 유닛 테스트의 사각을 보완.
- **의도적으로 하지 않은 것(비용 절제 판정)**: ① 사내 배포 서버(registry) 하드닝 — 병목은 배포가 아니라 채택이라는 판단으로 동결 ② 자체 화면 빌더 플랫폼 — 직접 구축 대신 기존 도구 활용(BUY) 판정 ③ drag-and-drop 디자인 플랫폼 — 사용자 관찰 결과를 반대 증거로 NO-GO. 매 판정은 별도 심의(gonogo)로 기록.
- **정직 보고 원칙**: 검증 통과(PASS)를 보고할 때도 "검사하지 못한 영역"을 반드시 명시 — 아래 §7이 그 결과물.

## 8. 하반기 계획

1. **Vue·Flutter 화면 부품 착수** — 플랫폼 1개·Button 1종부터 (확장 게이트 해제 완료, ADR-047). 다크모드·터치 타깃 등 웹에 없던 축은 착수 시 별도 결정.
2. **채택 확산** — 두 번째 실소비처 확보. 비개발자도 스스로 화면을 만들 수 있는지(self-serve) 검증: 사전점검 도구(precheck) → 페어 세션으로 장벽 위치 관찰.
3. **표준 권고 상신** — "신규 사내 웹앱은 `@wonik/web` 기본 검토"를 권고 가이드 한 줄로 올리는 안(임원 보고 초안 기작성).
4. **HMI Figma 변수 정합** — 상태 변수 15개를 ADR-037 원칙 값으로 갱신.
